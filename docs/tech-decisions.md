# Technical Decisions

Technical choices made by the development team, one line per decision, newest first. Product decisions are in [decision-log.md](decision-log.md).

| Date | Decision | Reason | Alternatives considered |
| --- | --- | --- | --- |
| 2026-11-02 | The copy price is a one-row table, `copy_price` (migration 0013, 30 centavos), next to the anillado prices in `anillado_sizes`. Only the logged-in operator can read it. The global report is computed from the detailed report's department totals (`buildGlobalReport` in `src/domain/globalReport.ts`), in integer centavos. A size without a price stops the report instead of billing 0. | #8: prices change once a year and editing them comes after the MVP, so a price change must need no deployment. Deriving one report from the other keeps both in agreement, with the grouping in one place. | A constant in the code; a generic key/value settings table (values as text, no type checks); computing the global report again from the entries. |
| 2026-10-31 | The reports are PDFs built in the browser with pdfmake (0.3), with its built-in Roboto font. pdfmake is loaded with a dynamic `import()` only when a report is generated, so Vite puts it in separate files (about 1.6 MB with the fonts) that the shared device never downloads. The PDF downloads as a named file (`reporte-detallado_23-10-2026_22-11-2026.pdf`, `_parcial` for an open period). The document is a plain object built by a pure, tested function (`src/reports/`); the numbers come from `src/domain/`. | #7, #8: the output must be a PDF on letter paper. A library gives the same file on every computer, with page numbers and repeated table headers, and nothing for the operator to set in a print dialog. A download is not blocked like a new tab opened after loading, and the name helps her records. | Printing a web page to PDF from the browser; opening the PDF in a new tab; jsPDF. |
| 2026-10-31 | The operator's computer must also have Chrome in Spanish, like the shared device (2026-10-17 decision): the native date fields of her screens (Cambiar cierre, edit and manual entry) follow the browser's language, not the page's `lang="es"`, and show mm/dd/yyyy in an English Chrome. To be confirmed by the PO with the operator. | Found while testing #52: the dates written by our code (dd/mm/yyyy) and the date field disagreed in an English browser. Keeps the native calendar and needs no code. | Our own dd/mm/yyyy date control for the whole app (a backlog item for the PO if wanted). |
| 2026-10-30 | Billing periods live in the database (migration 0011), named by their month (`2026-11-01` = the period ending by default on 22/11). Only the end dates the operator moved are stored (`period_ends`); a start is always the previous end + 1, so gaps and overlaps cannot exist. An end's limits come from the period's month, not from its actual start: from the 23rd of the month before to the 21st of the month after (migration 0012, after early closes chained in testing). The rule is in SQL only (`periods_as_of`, `period_end_limits`, `apply_period_end`, with "today" as a parameter); the browser calls `list_periods`, which also returns each period's limits for the date field, and `set_period_end` (admins only). The first period's start is one function, `first_period_start()`. Database rules are tested by SQL scripts in `supabase/tests/`, run in the test project inside a rolled-back transaction. | #52: the operator moves end dates, and the entry list, both reports and the #3 warning must agree; one rule in one place. Testing with a pretended "today" checks the PO's examples on any day. | A table with every period's start and end (overlaps possible, needs extra checks); the rule duplicated in TypeScript; the Supabase CLI with pgTAP tests (needs Docker). |
| 2026-10-27 | Two Supabase projects: `fotocopias-upb-dev` for local development and Vercel previews, production for the live app only. The same `VITE_SUPABASE_*` names have Production values (real database) and Preview/Development values (test database) in Vercel; `.env.local` uses the test project. Migrations go to the test project first, then to production after the merge. This replaces the 2026-10-24 decision to share one database. | #44: tests and demo data must never touch the real entries or reports. Free plan allows two projects. | One project with a separate schema for tests; the Supabase CLI with local Docker databases. |
| 2026-10-27 | The browser roles keep only the table access the app uses (migration 0010): nothing on `entries` and `entry_anillados`, reading only on `areas` and `anillado_sizes`. New tables follow the same rule. | Supabase's default grants rely on RLS alone, which does not cover TRUNCATE; found when comparing the two projects' permissions. | Keeping the default grants and relying on RLS. |
| 2026-10-26 | The operator registers entries for others with `register_manual_entry` (migration 0009, admins only, no PIN), which sets `entries.manual`, shown as "Ingreso manual" in her list only. The entry checks of edits and manual entries live in one internal function, `check_entry`. The edit form doubles as the manual-entry form, and a new manual entry can be undone (deleted) from the undo bar. | One place for the rules, so "validated like any other entry" cannot drift; one form to maintain; undo behaves the same for every change. | A separate form for manual entries; duplicating the checks in each function. |
| 2026-10-26 | The operator edits and deletes with admin-only functions (`update_entry`, `delete_entry`, migration 0008). Undo uses `restore_entry`, which puts back the version the app had before the change (same number and saved time, re-inserted with `overriding system value`); that version is kept only in the browser until her next change. Edits set `entries.modified_at`, shown as "Modificado" in her list only. | One function undoes both edits and deletes, and the database keeps no history (decision log 2026-10-14). | Soft delete with a `deleted_at` column (keeps deleted data); a history table of old versions. |
| 2026-10-26 | "At least 1 copia or 1 anillado" is checked in the browser (`checkEntryContents`) for a quick message and in the database (`entry_is_empty`, used by `register_account_entry` and `update_entry`). The staff form's department field is the shared `AreaSelect`, also used by the edit form. | The database check holds even if the browser is bypassed; one rule and one department field for staff and operator. | Checking only in the browser; a separate department field in the edit form. |
| 2026-10-25 | The operator's entry list loads one billing period at a time through `list_entries(from, to)` (migration 0006, admins only), selected by service date (`entry_date`); filtering and sorting happen in the browser, in pure functions in `src/domain/entryList.ts`. | A period is at most ~500 entries: one request, then instant filtering as she types. The browser still has no direct access to `entries`. | Filtering and sorting in SQL, one request per change; RLS read policies for admins on `entries` and `entry_anillados`. |
| 2026-10-25 | The operator logs in with Supabase Auth (email + password); Supabase stores only a bcrypt hash. Being logged in is not enough: she must be listed in the `admins` table (migration 0005), and every admin function checks `is_admin()`. Public sign-ups are switched off in the dashboard. Admin users are created by the developer in the dashboard, and the developer resets a forgotten password there (no reset email yet). | Sessions, tokens and password hashing are built in; nothing to write ourselves. The `admins` check means a stray auth user (e.g. sign-ups switched on by mistake, the default) can do nothing. | Our own password check in a function, with our own sessions; treating any logged-in user as the operator; a reset email flow. |
| 2026-10-25 | The operator's area is the address `/admin` (shown as "Admin"), chosen in `App.tsx` from the URL path, with no router. `vercel.json` rewrites every path to `index.html`. No automatic logout yet: the PO will ask the operator for the period. | Nothing operator-related appears on the shared device; she bookmarks the address. Without the rewrite, opening or reloading `/admin` gives a 404 on Vercel. | react-router; an "Operador" button in the staff navigation. |
| 2026-10-24 | Saving without a PIN is switched off: migration 0004 drops `register_entry`, so every new entry goes through `register_account_entry`. Entries saved before keep `account_id = null`. 0004 is applied only after the new form is deployed to production. | Sprint 2 requirement: every entry is verified against an account and PIN. The database is shared, so dropping it earlier would break saving in production. | Keeping `register_entry` as a fallback (any URL holder could save without a PIN); deleting the old entries to make `account_id` required. |
| 2026-10-24 | Staff choose their name with our own search field (`AccountPicker`): matching names appear as buttons, filtered in the browser ignoring case and accents with the same rule as `normalize_name`. One form: name at the top, PIN just above Guardar, checked when saving; the outside-department warning is an inline box with a required checkbox. | `<datalist>` does not ignore accents and accepts any typed text on Android; a separate login screen would add a tap and a PIN-check function. | `<datalist>`; a login screen before the form; the browser's `confirm()` dialog for the warning. |
| 2026-10-24 | Entries with an account are saved by a new function, `register_account_entry` (account id + PIN), next to the old `register_entry`, which is dropped in #40 once the login screen is deployed. Entries get a nullable `account_id`; `name` is kept and filled from the account at save time. Wrong PINs are not limited (no lockout). | Preview and production share one database, so changing `register_entry` in place would break saving in production until #39 ships. Keeping `name` leaves old entries and reports unchanged. No lockout: PO accepted the risk, since the URL is not public and the operator watches the shared device; a script with the URL could still guess a 4-digit PIN. | Changing `register_entry` in place; showing only the account's current name; locking an account after N wrong PINs. |
| 2026-10-24 | Preview deployments (branches) and production (`main`) use the same Supabase project; the `VITE_SUPABASE_*` env vars in Vercel apply to all environments. A second project for testing is added before tests with real users. | Only test data so far; one database means migrations are applied once. | A separate Supabase project for previews from the start. |
| 2026-10-24 | PIN fields are text fields with the numeric keyboard (`inputMode="numeric"`) and digits hidden by CSS (`-webkit-text-security: disc`), not `type="password"`. | Chrome offers to save passwords on a shared device, which would keep one person's PIN for everyone. | `type="password"` with `autocomplete` hints, which Chrome often ignores. |
| 2026-10-24 | Screens are switched with a `view` state in `App.tsx`, without a router library. | Two screens, no need for their own URLs; nothing to learn or install. | react-router; to revisit with the operator screen (#4). |
| 2026-10-24 | Staff accounts are our own `accounts` table, with no Supabase Auth. The PIN is stored only as a bcrypt hash (`pgcrypto`), and the browser cannot read the table: it only calls `create_account` and `list_accounts` (names and departments, never the hash). From #29, the PIN is checked in the same function that saves the entry. This will replace the 2026-10-15 rule that anyone with the URL can save entries. | The shared device must not keep a login session; "logged out after each entry" then just means forgetting the PIN. A 4-digit PIN needs no email or password. | Supabase Auth with one hidden email per staff member; checking the PIN in the browser. |
| 2026-10-24 | Account names are unique ignoring case, accents and extra spaces, enforced by a unique index on `normalize_name(name)` (`unaccent` + `lower`). | PO: "maría lopez" is the same name as "María López". An index also catches two people saving the same name at the same moment. | Checking for duplicates in the browser before saving. |
| 2026-10-24 | Database functions fail with short English codes (e.g. `name_taken`); the app turns each code into a Spanish message. | All user-facing text stays in the frontend, in one language and one place. | Spanish messages written inside the SQL functions. |
| 2026-10-20 | Styling is hand-written CSS in `src/index.css`, with all colors and sizes as design tokens (CSS variables in `:root`); UPB navy `#091859` and gold `#f9b93d`, taken from upb.edu. Choosing a UI toolkit is deferred to Sprint 2, before the report screens. | One screen and a 2-hour timebox; the look will change after the operator's feedback, and tokens make that a few-line change. | Tailwind CSS; a component library (MUI, Mantine). |
| 2026-10-17 | The form uses the browser's native date field; the tablet must be set to Spanish so it shows dd/mm/aaaa. Dates our own code displays are always formatted dd/mm/yyyy. | Native touch calendar with no extra code; the date is rarely changed (defaults to today). | Our own dd/mm/yyyy date control, the same on every device. |
| 2026-10-17 | Migrations are applied by pasting them into the Supabase SQL Editor. | One database and one developer; avoids installing and linking the Supabase CLI during the first sprint. | Supabase CLI (`supabase db push`), to revisit if a second environment (e.g. testing) is added. |
| 2026-10-17 | Entries are saved through a database function (`register_entry`, security definer) called with `rpc`; the browser cannot read, change or delete entries directly. | An entry and its anillados are saved together or not at all (one transaction), and the public key cannot be used to read or erase records. | Two direct inserts from the browser (`entries`, then `entry_anillados`) with RLS insert policies. |
| 2026-10-17 | Entries reference departments by id (`areas` table), and anillados by size (`anillado_sizes` table). Departments are hidden with `active = false`, never deleted. | Renaming a department does not break old entries; old reports keep working when a department is removed. | Storing the department name as text in each entry. |
| 2026-10-17 | Vitest for unit tests. | Reuses the Vite configuration, so TypeScript tests run with no extra setup. | Jest (needs its own TypeScript transform). |
| 2026-10-17 | oxlint as the linter, as generated by the Vite template. | Template default, very fast, almost no configuration. | ESLint (more plugins, slower, more configuration). |
| 2026-10-15 | Money is stored and computed as integer centavos, and formatted as Bs only for display. | Binary floating point cannot represent 0.30 exactly, so sums drift; the product promises zero calculation errors. | Floating-point numbers; Postgres `numeric` everywhere. |
| 2026-10-15 | Every database schema change is a numbered SQL migration in `supabase/migrations/`, committed to git. | The schema can be rebuilt, reviewed and traced, like code. | Editing tables only in the Supabase dashboard. |
| 2026-10-15 | The browser talks to Supabase directly with the public anon key, protected by Row Level Security policies. | No backend server to write, deploy or maintain. Anyone with the URL could insert entries, which is acceptable for the pilot (like an open paper notebook). | A custom API (e.g. Vercel serverless functions) in front of the database. |
| 2026-10-15 | TypeScript instead of JavaScript. | Type errors are caught at build time instead of on the tablet; better editor help. | Plain JavaScript. |
| 2026-10-15 | Vite single-page app instead of Next.js. | No server rendering or SEO needed; fewer concepts to learn for a first web app. | Next.js; Create React App (deprecated). |
